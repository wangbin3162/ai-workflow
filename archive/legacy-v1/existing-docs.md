# 工程已有规则文件时怎么处理

目标：不覆盖用户的东西，也不丢任何内容；新工作流的入口 `AGENTS.md` 能把读者带到旧规则。

## `install.sh` 对各类文件的处理

| 已有文件 | 处理 | 原因 |
| --- | --- | --- |
| `AGENTS.md`、`LESSONS.md`、`docs/code-standards.md`、`.claude/loop.md`、`docs/ai-loop-architecture.md`（非空） | **原样搬**到 `docs/legacy/<文件名>`（已跟踪用 `git mv`，保留历史；重名加序号），再在原位置写新文件 | 新文件必须占这个路径才能被 agent 工具读到；旧内容一字不改地留在 legacy，随时能对照 |
| `CLAUDE.md` 且只是 `@AGENTS.md` 转发 | 直接替换，不保留 | 没有信息量 |
| `CLAUDE.md` 有其他内容（含 `@其他文件` 导入） | 同上，搬到 `docs/legacy/CLAUDE.md` | 里面的导入和说明不能丢 |
| 完全空的文件（0 字节） | 删掉重建 | 没有内容可保 |
| 只有一两行的「近乎空」文件 | 和普通文件一样 **MOVE**，不当作空文件 | 一行字也可能是用户有意写的规则，丢了无法判断；搬走的成本只是多一个 legacy 文件 |
| 子目录里的 `AGENTS.md`（如 `server/AGENTS.md`） | **不动**，只在新 `AGENTS.md` 的「项目原有规则」表里引用 | 它是模块级规则，路径本来就对 |
| `.cursorrules`、`.github/copilot-instructions.md`、`GEMINI.md` | **不动**，只引用 | 属于其他工具 |
| `.gitignore` | 只追加一个标记块，不改已有行 | 加法安全 |
| `README.md` | 不碰 | 不是 agent 规则 |

## 前置条件（脚本会检查）

- 要搬或要写的文件有未提交改动、或未被 git 跟踪 → 停下。没有历史保护的文件被改，出了问题找不回来。
- 存在 `.ai/` 或 `scripts/ai-loop.sh`，但 `AGENTS.md` 没有 `ai-loop-init:v1` 标记 → 停下，需要人决定是合并还是换目录。
- 已有标记 → 视为已初始化，什么都不做。

## 搬走的 CLAUDE.md / AGENTS.md 里的 `@路径` 导入

`@docs/extra.md` 这类导入是相对仓库根的；文件搬进 `docs/legacy/` 后导入会失效。脚本会把被导入且存在的文件直接加进新 `AGENTS.md` 的引用表（原位置不动）。不要去改 legacy 文件里的路径。

## 提炼到什么程度

提炼 = 把**已核实、会影响 agent 怎么干活**的事实（构建 / 测试命令、红线、关键约定）写进新 `AGENTS.md` 对应小节，并保留指向来源文件的链接。被 `@` 导入的文件、`.cursorrules`、子目录规则只引用、不抄——抄进去就有两份，迟早漂移。最多留一行指针式摘要。

## 搬完之后你要做的

1. 打开 `docs/legacy/AGENTS.md`（若有），把里面**已核实**的构建 / 测试命令、红线、约定提炼进新 `AGENTS.md` 的对应小节，并保留到 legacy 文件的链接。只写你核对过的；不要整段复制（复制品会漂移，两处不一致时读者不知道信哪个）。
2. 新 `AGENTS.md` 里「项目原有规则」表已由脚本生成：旧规则管项目的构建 / 约定 / 架构，**新文件管任务池流程与护栏**；冲突时让 agent 先停下问人。如果你发现两边确有冲突，在汇报里指出，不要自己裁决。
3. 旧 `LESSONS.md`（若有）：不要把旧条目硬塞进新格式。旧内容在 `docs/legacy/LESSONS.md`；新 `LESSONS.md` 保持「暂无」，下一次真实返工再按新格式写。可以在新文件「已毕业」小节加一行指向 legacy 的说明。
4. 旧 `docs/code-standards.md`（若有）：它的有效标准要合并进新文件对应小节（逐条核对，保留其证据和数字），而不是丢掉；合并不了的写 `TODO:` 并列进汇报。

## 汇报里要写清

`原路径 → docs/legacy/…` 每一条；哪些内容被提炼进新文件、哪些只保留在 legacy；发现的冲突或疑点。
