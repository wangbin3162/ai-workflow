AI-WORKFLOW · 可视化流转指南

任务怎么流转

人写任务。AI 先只读；有歧义就停下来等你批准。改代码、送审之后，审查和合并仍由你做。AI 不合并、不 push、不删除 worktree。

执行规则以 README.md 为准

01 · 初始化

摆好任务池

在目标仓库的会话里说一次。只生成 .ai-workflow/，不改项目其他文件。

/ai-workflow init

02 · 整理任务

先出草稿

手写，或让 AI 拆 list/ 里的清单。你没明确要写入之前，不会进 inbox。

/ai-workflow task …

03 · 执行任务

领取一条

只领 inbox 里 status: new 的任务。讨论中和阻塞中的不能领。

/ai-workflow 处理 T-20260101-001
1 / 7
inbox 收件 doing 进行 review 审查 done 归档 blocked 拒绝/阻塞 审查通过后留 review；审查不通过退回 blocked。

手写任务

你怎么操作

按业务路径指引。字段和命令细节以 README.md 为准，配置见 CONFIG.md，任务格式见 TEMPLATE.md。

主路径

  1. 复制 TEMPLATE.md 为 inbox/T-20260101-001.md。id 与文件名一致，status: new。验收标准写可执行的命令；没核实的写 TODO。
  2. 说 /ai-workflow 处理 T-20260101-001。AI 加锁、把文件移到 doing、准备分支 ai/T-20260101-001 的 worktree（位于平级 .ai-worktrees/）。
  3. AI 只读探索，不改业务代码。没有重要歧义就直接实施。
  4. AI 只在 worktree 里改代码，把命令、目录、退出码、结果写入「验证记录」。没跑就写「未运行」。risk: high 只出方案，不改代码，送审时不能有 commit。
  5. 工作区干净、验证记录非空后送审，文件进入 review。到这里停止，不合并。
  6. 你看 diff 和验证记录。若审查通过：明确说审查通过，文件仍留在 review；若审查不通过：说明拒绝意见，任务转为 blocked 退回 inbox。
  7. 人工合并由你执行。告诉 AI 目标分支、合并提交、方式和你的原话。核对通过后才进入 done。

遇歧义

  1. 业务口径、接口、数据、权限、兼容或范围说不清时，AI 不能靠默认假设开工。
  2. AI 写「讨论」，把 status 改为 needs-discussion，文件移回 inbox，删除锁。worktree 和已有 diff 保留。
  3. 你补全「方案」。AI 计算方案正文的 sha256，写上 plan_version。
  4. 你明确说「批准版本 N」。只写方案，或 AI 说可行，都不是批准。
  5. 你要求恢复后，AI 重新计算 sha。版本、sha、批准人和原话一致，才回到 doing 继续做。
  6. 方案改过，或版本对不上，旧批准作废，不能恢复。

阻塞与拒绝

  1. 审查不通过或做不下去：status 改为 blocked，文件回到 inbox，删除锁，现场 worktree 和代码提交保留。
  2. blocked 和 needs-discussion 都在 inbox，但不能当新任务领取。
  3. 你补充信息、给出修改意见并确认可以重做后，把 status 改回 new，AI 即可重新认领并实施。
  1. 1. 任务由你写

    /ai-workflow task 默认只给草稿。你确认后才写入 inbox，仍然不领取、不实现。

  2. 2. 批准要说出版本

    只有「批准版本 N」算数，而且只用于从讨论恢复。主路径没有歧义时不需要这一步。

  3. 3. 审查通过 ≠ 合并

    通过后 status 是 review_approved，文件留在 review；若审查不通过则转为 blocked 退回 inbox。

  4. 4. 人工合并才归档

    merged_commit 必须在目标分支上。squash / rebase 不能用 sha 证明内容相同，必须写明。

文件停在哪

各状态对应的物理目录分布与职责边界。

inbox

new 可领取。needs-discussion 与 blocked 不可领取。list/ 只放清单，没有状态。

doing

claimed。同时有锁 .locks/任务id/，以及 worktree .ai-worktrees/任务id/。

review

needs_review 等人看。review_approved 是人已通过、尚未合并。审查被拒则转回 inbox/blocked。

done

done。有目标分支和合并提交证据。无代码任务在你确认后也可以归档。不删除分支和 worktree。

不会自动发生

  • 不合并、不 push、不建 PR、不改 CI、不发版。
  • 不删除 worktree 或分支，不 reset 你的改动。
  • 锁已存在就停。异常退出留下的锁，由人确认后删除。
  • 不覆盖已有任务文件，不自动迁移旧 .ai/。
  • 不把任务状态偷偷提交进业务分支。
  • 验收标准不能自行放宽。没跑的检查写「未运行」。

最佳实践与冲突处理

多 Agent 协作黄金流，以及应对文件交叉与合并冲突的防御机制。详见 README.md。

黄金工作流（推荐协作方式）

  1. 主会话规划拆分：需求放入 list/，运行 /ai-workflow task 拆分，人工确认后写入 inbox/。
  2. 多会话独立并行：在终端或 T3 开 2~3 个窗口，分别发送 /ai-workflow 处理 T-xxx。无需手动切换 worktree，各 Agent 自动在 .ai-worktrees/ 下隔离工作，互不干扰；遇到歧义在该会话直接与你讨论。
  3. 主工程统一审查与归档：各任务完成后在主工程审查 diff 并合并。全部完成后运行 /ai-workflow archive 一键归档并清理 worktrees 与分支。
  4. 心智建议：单会话盲目拉起大量子代理易触碰 API 速率限制，且遇到歧义时无法替人决策；多独立会话人机协同更稳健。

文件交叉与合并冲突防御

  1. 绝对不自动合入基准分支：所有开发均限制在独立 worktree 与分支，main 主分支永远保持干净安全。
  2. 模式 1：先后合并，后者在 worktree 中 rebase（最常用）：若任务 B 准备合并时与最新的 main 冲突，在任务 B 会话中指令 Agent：“rebase main 解决冲突并重跑测试”，绿灯后再行合并。
  3. 模式 2：前后依赖指定 base_ref：若任务 B 强依赖任务 A，在元数据中写 base_ref: ai/T-A，直接基于 A 的分支开工。
  4. 模式 3：核心模块大重构排期串行：涉及同一核心文件大面积重写时，拆分阶段排为先后顺序，不盲目并行。
