# 把一句话写成一条 inbox 任务

一句需求 → **一个** `.ai/inbox/T-YYYYMMDD-NNN.md`。转写的是任务说明，不是开工。

## 0. 前提

当前目录必须同时有 `.ai/templates/task.md` 和 `.ai/inbox/`。缺一就停下，告诉用户先在这个工程里用 ai-loop-init 初始化。不要自己建一套残缺目录，也不要写到别的仓库。

用户没有给出要做什么（只有「新增任务」四个字）就问一句需求，不要编。

## 1. 只读

1. 读 `.ai/templates/task.md`，新文件沿用它的章节，不改模板。
2. 用户点名了文件或目录：用仓库相对路径核对是否存在。不存在就在背景里照录原话，回复里写「路径未找到」。不要改猜另一个文件。
3. 验收标准里的命令只许来自本仓库 `docs/code-standards.md`「构建与检查」（或 `AGENTS.md`「构建与测试」）里已经写明的命令。没有核对过的命令不要写。没有测试可写时，写人工对照步骤和修改前后可区分的现象。
4. 分配 id：在 `.ai/inbox`、`doing`、`review`、`done`、`blocked` 里，找出今天 `T-YYYYMMDD-NNN` 和 `EXAMPLE-T-YYYYMMDD-NNN` 的最大 NNN，加 1，三位补零。文件名必须是 `T-YYYYMMDD-NNN.md`（不要 `EXAMPLE-` 前缀），front-matter 的 `id` 与文件名一致（`scripts/ai-loop.sh check` 会校验；`move_task` 用文件名当 id）。目标已存在就再加 1，不要覆盖。

日期用本机当天，`YYYY-MM-DD` / `YYYYMMDD`。

## 2. 转写

一条需求一个文件。用户没明确说「拆成几条」就不要拆。范围大到一轮做不完，在回复里说建议拆，文件仍然只写这一条。

| 字段 | 规则 |
| --- | --- |
| title | 一句话，去掉「帮我 / 请」。 |
| type | 有期望 vs 实际 → `bug`；改行为或样式 → `feature`；文档、脚本、不改产品行为 → `chore`。拿不准用 `feature`，回复里说明。 |
| priority | 用户没说就 `P2`。 |
| risk | **只有**明确不碰支付、鉴权、权限、依赖、CI、数据迁移、公共接口、数据格式时才写 `low`。纯样式、文案、且点名了范围 → `low`。拿不准写 `high`（循环只会出方案，不改代码）。 |
| status | `new`。`claimed_by` / `claimed_at` 留空，`attempts: 0`，`max_attempts: 2`。 |
| created | 今天。 |

正文：

- **背景**：用户要解决的事、点名的参考文件（相对路径）、改哪里。没说过的现状不要编。
- **验收标准**：每条都能观察或执行，且能追溯到用户原话。不新增用户没要的功能。样式类至少一条：人工对照 `<参考文件>`，写出改前改后可区分的现象。禁止「基本完成」「看起来不错」「跑一下测试」。
- **不要做**：保留模板里的三条，并写上这次范围外的（例如不改参考文件本身、不改列表的数据接口、不改其他页面）。
- **AI 记录区**：只留三个空标题，不要预填拆解。

front-matter 不要写行内注释，值里不要出现 ` #`。

## 3. 写入

只新增这一个文件。不改其他任务，不 `git add` / `commit`，不认领，不建 worktree，不按 `.claude/loop.md` 开工。

## 4. 回复

三到五行：文件路径、`id`、`type`、`priority`、`risk` 及一句话理由；没找到的路径；没写入的检查命令。下一步由人决定：改完文件后可以说「按 `.claude/loop.md` 处理一个任务」。

## 不要做

- 不实现需求，不改产品代码。
- 不把用户原话原样贴进验收标准就算完成；要改写成可验证条目，但不得加需求。
- 不覆盖已有任务文件。
