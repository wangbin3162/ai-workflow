# 验收标准

改动只有在以下每条都「通过」，或对无法执行的条目明确标注「未验证 / 未跑」并说明原因时，才算完成。
**跑过的检查写明结果；没跑的检查写「未跑」，不许省略。**
（这条不是道德要求，是格式要求——因为格式能被检查，道德不能。）

## 一、验收标准

### 1. 关键行为有能区分修复前后的检查

改 `scripts/ai-loop.sh` 的行为，要在 `scripts/test-ai-loop.sh` 里补一个用例。
把旧代码放回去跑新用例，应出现**真的 `FAIL`**，并点名具体行为；编译错误、跳过、断言缺失都不算。
反向验证：在可安全还原的自有改动上，手工改坏一处，确认用例变红；还原后确认变绿。

纯文档改动没有测试可跑：写明改了哪几处事实、和哪份源（脚本 / 命令输出）核对过。

### 2. 测试不碰真实环境

`scripts/test-ai-loop.sh` 只在 `mktemp -d` 的临时仓库里跑，用假 claude（`$TMP/claude-stub`）。
**不要对真实 `.ai/`、真实 worktree、真实 `claude` 跑测试。** 要对真实任务试跑，用 `DRY_RUN=1`（见第 4 条）。

### 3. 构建与检查

没有构建步骤。真实命令：

- `bash -n scripts/ai-loop.sh && bash -n scripts/test-ai-loop.sh` —— 语法检查
- `bash scripts/test-ai-loop.sh` —— 回归测试

**当前基线（实测值只记在这里）：** 27 个检查全部通过（2026-11-10 实跑）。基线变了就改这一行并带日期。

### 4. 尽可能真实使用

能对真实环境跑的，必须真跑一次：真任务、真 `claude`、真 worktree。
**跑不了的，明说「未验证」。没试过的东西，不建立在它之上，也不告诉用户它能用。**

本项目的「真实环境」指：在一个真实仓库里放一个小任务，`DRY_RUN=1 scripts/ai-loop.sh` 看候选，
再 `scripts/ai-loop.sh` 完整跑一轮。**在这一轮跑通之前，不宣称可以无人值守**；
`docs/ARCHITECTURE.md`「未验证与风险」里的条目随着真实运行逐条销项。

### 5. 范围检查

提交前看 diff：有没有和本次目标无关的改动？有就拆成独立提交。
夹带的改动会让审查无法判断哪一部分是本次要验证的。

### 6. 完成前自检

- 有没有超出任务范围？
- 有没有把没验证的事写成已完成？
- 有没有用 workaround 掩盖根因？
- 有没有留下临时文件、调试代码、无关改动？
- 锁释放了吗（`.ai-locks/`）？worktree 与分支名是否与任务 id 一致？`scripts/ai-loop.sh check` 通过吗？

## 二、提交信息

三段式，缺一段都算没写完：

```text
<scope>: <用户看到的变化，用行为描述，不用实现描述>

为什么：<谁报的 / 什么场景触发的 / 不这么改会怎样>
改了什么：<哪些行为面变了；边界在哪；哪些相邻情况保持不变>
跑了什么：<具体命令 + 具体结果数字>
没试过：<明确列出没验证的部分>
```

要求：

- **标题用行为描述**，不要写「更新」「优化 X」「重构 Y」。至少带上 scope（`loop` / `task` / `docs`）。
- **数字要具体**：不写「测试通过」，写「`bash scripts/test-ai-loop.sh` 23 个检查全过」。
- **「没试过」是必填项**，没验证的部分写「未跑」，不省略。
- 大改动（多个文件或行为面）必须有 body；只改错别字可以只有标题。
- 任务分支上的 commit 同样遵守；脚本自己提交的状态迁移（`ai: claim/review/...`）除外。

## 三、复盘

### 什么时候复盘

**按需，或发版前**（个人 / 小项目的校准值；`LESSONS.md` 体量上限 ≤ 5 条）。
**额外触发条件**：一次任务里出现**返工**（同一个东西改了两次以上）→ 立刻复盘一次。
项目变成多人 / 高频并行后，改成「每 ~20 个提交」，并同步调整 `LESSONS.md` 的体量上限。

### 怎么复盘

用一个独立会话（或独立 Agent）来读，不要用正在改代码的那个——它知道自己当时的想法，会替自己辩护。提示词：

```text
读最近 N 个提交的完整信息和 diff。回答三个问题：

1. 哪些是「修完又坏」或「改完又改」的？根因是什么？
2. 哪些改动其实不该合进来？（夹带、超出范围、没验证）
3. 哪些验证做太薄？（只说"应该没问题"、没真跑、没反向验证）

对每个发现，写成一条错题追加到 LESSONS.md：
规则（祈使句）→ 症状 → 根因 → 证据（commit + 事件）。
已存在的错题，复发次数 +1。

最后：有复发 >= 3 次的，移进 docs/code-standards.md，从错题本删掉。

只报你有证据的发现。没发现就明说没有——不要为了凑数编造错题。
```

没有独立上下文时也照跑，但**只报可机械核对的事实**（`git log` / `git show` 里直接能看到的），
跳过「验证够不够厚」这类判断，并在输出里明说这次是自审。

### 毕业规则

一条错题被**独立踩到 3 次** → 光靠「读一遍」拦不住 → 升级成常驻标准。

- 标准正文写进本文件「四、已毕业的规矩」。
- 从 `LESSONS.md` 删掉正文，只在「已毕业」里留一行指针。
- 「独立踩到」指分开的时间点，同一次任务里犯两回算一次。
